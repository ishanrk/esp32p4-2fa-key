time utc
2026 08 26 01 57 49

stage
01 repository and board baseline

problem
the board has BOOT and RESET keys but no separate user key

choice
use the BOOT key on GPIO35 as the candidate user presence input with active low conversion and an enabled internal pull up

reason
the official schematic connects Key2 between GPIO35 and ground and shows no discrete pull resistor at the switch

alternatives rejected
RESET cannot be read as an application input
an invented header GPIO would not be a proven physical button

files affected
docs/BOARD_FACTS.txt
components/p4_board/Kconfig
components/p4_board/p4_board.c

reconsider when
a physical level test contradicts the schematic or a dedicated user button is added

END DECISION

decision
0003

time utc
2026 08 26 01 57 49

stage
01 repository and board baseline

problem
the board exposes a CH343 debug Type-C connector a direct module USB Type-C connector and jumper selected Type-A OTG ports

choice
reserve the Type-C connector labeled USB as the native device candidate and keep logs on PWR USB TO UART

reason
the board schematic routes the USB Type-C H2 data pair directly as USB1P1 while PWR USB TO UART terminates at the CH343P

alternatives rejected
the CH343 connector is not the native USB controller
the Type-A bank adds host device jumper and hub routing that is unnecessary for the first device baseline

files affected
docs/BOARD_FACTS.txt
PROJECT_STATE.txt

reconsider when
on target USB enumeration proves a different controller connector mapping

END DECISION

decision
0004

time utc
2026 08 26 02 13 43

stage
01 repository and board baseline

problem
the initial IDF default selected ESP32 P4 revision v3.1 or newer but esptool proved the attached chip is revision v1.3

choice
enable CONFIG_ESP32P4_SELECTS_REV_LESS_V3 in sdkconfig.defaults and rebuild without force flashing

reason
IDF 6.0.2 uses different ROM linker scripts startup paths and peripheral workarounds for pre v3 silicon

alternatives rejected
forcing the incompatible v3.1 image would bypass a valid safety check
leaving the default would make the physical board baseline unusable

files affected
sdkconfig.defaults
docs/BUILD.txt
PROJECT_STATE.txt

reconsider when
the hardware target changes to ESP32 P4 revision v3 or newer

END DECISION

decision
0005

time utc
2026 08 26 02 48 17

stage
02 crypto accelerator proof

problem
ESP IDF v6.0.2 bundles Mbed TLS 4.1.0 where the old low level SHA GCM and ECDSA headers are private implementation interfaces

choice
use the public PSA Crypto API family consistently for SHA 256 AES 256 GCM and P 256 operations

reason
the installed ESP IDF tests use PSA and its dispatch reaches the configured Espressif SHA AES GCM and general ECC drivers without depending on private headers

alternatives rejected
including mbedtls private headers would tie project code to unsupported internals
mixing PSA and legacy low level APIs would add state and error handling without a hardware path benefit

files affected
docs/CRYPTO_PATHS.txt
components/p4_crypto

reconsider when
the pinned ESP IDF public crypto surface changes

END DECISION

decision
0006

time utc
2026 08 26 02 48 17

stage
02 crypto accelerator proof

problem
the IDF default enables the dedicated ECDSA verifier and software fallbacks even though this project must prove general P 256 ECC and only uses AES GCM and P 256

choice
disable dedicated ECDSA sign and verify paths AES software fallback unsupported curve ECC fallback and non AES GCM fallback

reason
the eFuse signer cannot represent independent WebAuthn credential keys and the dedicated verifier would make P 256 verification bypass the general ECC proof

alternatives rejected
leaving verify enabled would make the public verification route ambiguous
enabling the eFuse signer would require irreversible provisioning and the wrong key model
keeping unrelated fallbacks would weaken the release configuration proof

files affected
sdkconfig.defaults
components/p4_crypto/include/p4_crypto_check.h
scripts/check_crypto_config.py

reconsider when
the project adds a justified curve or non AES GCM use case or targets different silicon

END DECISION

decision
0007

time utc
2026 08 26 02 48 17

stage
02 crypto accelerator proof

problem
the pre v3 ESP32 P4 bootloader disables its SAR ADC entropy source before the application and the project does not initialize an RF subsystem

choice
crypto_init will call the supported bootloader_random_enable function before PSA initialization and keep the entropy source enabled

reason
the installed public header permits application use when RF is absent and esp_fill_random otherwise has only pseudo random state after the bootloader disables the source

alternatives rejected
using esp_fill_random without an active entropy source would not satisfy credential key requirements
direct register access would bypass the supported IDF flow
a software PRNG seeded after entropy is disabled cannot restore true entropy

files affected
docs/CRYPTO_PATHS.txt
components/p4_crypto/p4_crypto.c

reconsider when
the application needs the ADC or RF subsystem or targets revision v3 TRNG silicon

END DECISION
