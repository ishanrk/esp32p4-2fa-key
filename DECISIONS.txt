0007

time utc
2026 08 26 02 48 17

stage
02 crypto accelerator proof

problem
the pre v3 ESP32 P4 bootloader disables its SAR ADC entropy source before the application and the project does not initialize an RF subsystem

choice
crypto_init will call the supported bootloader_random_enable function before PSA initialization and keep the entropy source enabled

reason
the installed public header permits application use when RF is absent and esp_fill_random otherwise has only pseudo random state after the bootloader disables the source

alternatives rejected
using esp_fill_random without an active entropy source would not satisfy credential key requirements
direct register access would bypass the supported IDF flow
a software PRNG seeded after entropy is disabled cannot restore true entropy

files affected
docs/CRYPTO_PATHS.txt
components/p4_crypto/p4_crypto.c

reconsider when
the application needs the ADC or RF subsystem or targets revision v3 TRNG silicon

END DECISION

decision
0008

time utc
2026 08 26 03 01 35

stage
02 crypto accelerator proof

problem
the fixed GCM API has separate ciphertext and tag buffers while the pinned PSA multipart driver requires exclusive input and output ranges and can emit tentative plaintext before tag verification

choice
use PSA multipart GCM reject all output to input overlap reject overlapping ciphertext and tag outputs and clear the full plaintext destination after every processing failure

reason
multipart GCM maps to the fixed API without allocation while the strict alias policy satisfies the PSA buffer contract and explicit clearing prevents a caller from receiving unauthenticated plaintext

alternatives rejected
exact in place operation is outside the pinned exclusive buffer contract
allowing partial overlap could corrupt data before authentication
returning the tentative output after a failed tag would expose unauthenticated plaintext

files affected
components/p4_crypto/p4_crypto_gcm.c
docs/CRYPTO_PATHS.txt

reconsider when
the pinned PSA driver documents a safe in place contract or the public API shape changes

END DECISION

problem

stage
02 crypto accelerator proof

problem
PSA offers randomized and deterministic ECDSA algorithms and the stage must record the actual nonce mode without assuming signatures differ

choice
use randomized PSA ECDSA with SHA 256 for P 256 signing

reason
the installed builtin ECDSA implementation draws the per signature nonce through the configured PSA external RNG hook and therefore the enabled ESP32 P4 entropy path

alternatives rejected
deterministic ECDSA is supported but would not exercise the hardware random source for each nonce on this general ECC route
asserting repeated signatures differ would turn a permitted implementation detail into a correctness requirement

decision
0011

time utc
2026 08 26 03 18 26

stage
02 crypto accelerator proof

problem
the public Mbed TLS DER converter rejects trailing data but can accept some nonminimal length and INTEGER encodings that strict DER must reject

choice
prevalidate the complete DER shape with a small host testable canonical checker then parse and re encode with the public Mbed TLS PSA utility and require an exact byte match

reason
the pure checker rejects long form lengths negative integers redundant padding and trailing bytes while the installed converter remains responsible for the raw r and s conversion

alternatives rejected
using only the converter would accept some alternate BER encodings
returning the 64 byte PSA r followed by s format would violate the public API
implementing ECDSA arithmetic or ASN1 big integer conversion in project code is unnecessary

files affected
components/p4_crypto/p4_crypto_p256.c
components/p4_crypto/p4_crypto_p256_util.c

reconsider when
the pinned public converter itself guarantees the same strict canonical policy

END DECISION

stage
02 crypto accelerator proof

problem
raw target logs can contain unrelated device output and concatenated sessions while a missing board run must never be mistaken for passing evidence

choice
generate a deterministic report through a whitelist parser that requires one ordered 23 test and 9 benchmark session and labels an intentionally omitted log as target data unavailable

reason
strict names counts ordering repetitions summaries configuration and size validation prevents partial stale or failing evidence from producing PASS while whitelisted extraction keeps unrelated log data out of the tracked report

alternatives rejected
copying the raw log would retain unrelated device data
using the last result for duplicate names could accept a concatenated reboot session
treating a supplied malformed log as unavailable would hide a reproducible failure
requiring a target log when no board is attached would conflict with the project unavailable evidence policy

files affected

tests/host/test_crypto_report.py
docs/generated/CRYPTO_REPORT.txt

the target result grammar or required crypto test inventory changes

decision
0016

time utc
2026 08 26 04 11 46

stage
02 crypto accelerator proof

problem
a valid target result session could come from a different application image than the supplied build evidence

choice
optionally read the ESP application image descriptor and require its full ELF SHA 256 value to begin with the boot fingerprint captured in the target log

reason
ESP IDF embeds the ELF hash in the fixed application descriptor and prints its configured prefix at boot so the comparison ties a supplied target log to a supplied build without relying on timing

alternatives rejected
leaving the two evidence files unrelated would permit stale but individually valid records
invoking an external image inspection package would add an unnecessary environment dependency
claiming a full cryptographic binding would overstate the strength of the nine hexadecimal character boot prefix

files affected
scripts/crypto_report.py
tests/host/test_crypto_report.py
docs/generated/CRYPTO_REPORT.txt

reconsider when
the ESP image descriptor layout changes or the firmware prints the complete ELF SHA 256 value

END DECISION
