ENTROPY EVIDENCE

The ESP32-P4 v1.3 bootloader enables the SAR ADC entropy source and disables it
before entering the application. Without RF or that source ESP-IDF documents
esp_random output as pseudo random only. crypto_init therefore re-enables the
supported source with bootloader_random_enable before PSA initialization and
keeps it enabled. The installed bootloader_random.h explicitly permits this
from application code when the RF subsystem is not initialized. P4Key does not
use Wi-Fi Bluetooth or the ADC in this profile.

The selected public PSA API has no per-operation application RNG callback.
ESP-IDF configures the PSA external RNG hook, and the installed
mbedtls_psa_external_get_random implementation calls esp_fill_random. PSA key
generation and randomized ECDSA therefore use the same enabled source directly;
an unused project callback would not change that route.

FALLBACK POLICY

CONFIG_MBEDTLS_AES_SOFT_FALLBACK is disabled.
CONFIG_MBEDTLS_ECC_OTHER_CURVES_SOFT_FALLBACK is disabled.
CONFIG_MBEDTLS_GCM_SUPPORT_NON_AES_CIPHER is disabled.
CONFIG_MBEDTLS_AES_ONLY_128_BIT_KEY_LENGTH is disabled so AES-256 remains valid.

The project uses only P-256 and AES-GCM. Hardware SHA is selected through the
ESP-IDF PSA SHA driver. The SHA source name block_mode_fallback means hardware
block mode when DMA cannot reach a buffer; it does not mean software SHA.

The PSA multipart GCM route maps cleanly to the separate ciphertext and tag
API without allocation. It exercises hardware AES and the configured partial
GCM port but not the one-shot whole-message GCM DMA helper. All output-to-input
overlap, including exact in-place operation and partial overlap, is rejected;
the ciphertext and tag output ranges must also be disjoint. This follows the
pinned PSA configuration's exclusive-buffer contract. Authentication is
checked after tentative plaintext can be written, so gcm_open explicitly
clears the full output region on any failure after processing starts.

The target-only gcm_hw_one_shot test separately calls public psa_aead_encrypt
with a 64 byte nonzero NIST payload and internal DMA-capable input and output.
Those conditions satisfy the pinned esp_aes_gcm_input_support_hw_accel checks
and reach esp_crypto_aes_gcm_encrypt through esp_aes_gcm_crypt_and_tag and
esp_aes_process_dma_gcm. The known answer proves correct target operation while
the enabled symbols and linked installed sources prove route selection.

CONFIG_MBEDTLS_AES_SOFT_FALLBACK exists in Kconfig but has no consumer in the
pinned C or CMake source. Keeping it disabled records policy; hardware proof
comes from CONFIG_MBEDTLS_HARDWARE_AES and the selected Espressif source path.

SECURITY BOUNDARY

No eFuse is read written provisioned or modified by this stage. Secure Boot and
Flash Encryption stay disabled. Per-credential private scalars remain visible
to software long enough to export wrap and sign, and temporary copies must be
cleared. This is not a claim of hardware-protected credential keys.

P256 OPERATION DETAILS

P4Key selects randomized PSA ECDSA with SHA 256. The installed builtin ECDSA
implementation obtains each nonce through the PSA external RNG hook described
above. Public derivation and signing call general P 256 scalar multiplication;
verification calls the builtin ECDSA multiplication path because both dedicated
ECDSA peripheral options are disabled. Those multiplications reach ecc_alt.c
and esp_ecc.c, where the ESP32 P4 constant-time hardware multiply mode is set.

Private scalars are accepted only in the fixed range 1 through group order
minus one and PSA import validates them again. Public points use the 65 byte
uncompressed form. PSA import checks the point through the configured hardware
point verifier. P 256 has cofactor one, so an accepted finite on-curve point is
already in its prime-order subgroup.

PSA signatures are 64 byte raw r followed by s internally. The public wrapper
converts them with the installed Mbed TLS PSA utility and exposes only canonical
ASN.1 DER. Verification first enforces short minimal lengths and positive
minimal INTEGER encodings, then parses and re-encodes the signature and requires
an exact match. This rejects trailing bytes and alternate BER encodings.

TARGET PROOF PROFILE

CONFIG_P4KEY_CRYPTO_SELFTEST and CONFIG_P4KEY_CRYPTO_BENCH default off. The
sdkconfig.crypto-test.defaults profile enables them only in build/crypto-test.
The attached revision v1.3 board passed all 23 named tests and all 9 bounded
benchmarks through Windows COM7. Logs contain test names status numeric failure
details and timing only. Timing is supporting data and is not a constant-time or
hardware-selection claim.
