P4KEY CODEX ENGINEERING CONTRACT

PROJECT GOAL

Build P4Key

A small real USB FIDO2 WebAuthn roaming authenticator for an ESP32 P4 Waveshare board

The first release must do one thing well

A browser sees the board as a security key
A real website can register it
A real website can later authenticate with it
The user presses a physical button for each operation
The useful ESP32 P4 crypto hardware handles the cryptographic work

The target release is deliberately narrow

CTAP2 over USB HID
FIDO_2_0 behavior sufficient for normal WebAuthn registration and assertion
ES256 only
non discoverable credentials only
packed self attestation
physical user presence
hardware backed SHA 256
hardware backed P 256 operations through the general ECC accelerator
hardware backed AES GCM credential wrapping
hardware TRNG
optional eFuse HMAC root after the ordinary device works

Do not add PIN support
Do not add discoverable credentials or passkeys
Do not add CTAP1 U2F
Do not add NFC Bluetooth WiFi TOTP HOTP PIV OpenPGP SSH agent support
Do not add PQC
Do not add secure boot flash encryption OTA or custom PCB work in the required v0.1 path
Do not add a display dependency
Do not add an account database
Do not create a browser extension
Do not redesign the protocol

The device must interoperate through normal browser and operating system FIDO support

Use ESP IDF v6.0.2 unless the existing repository already pins a compatible version and changing it would destroy working code

Use the official Espressif TinyUSB component
Pin espressif esp_tinyusb 2.2.1 unless a later compatible version is already locked and proven in the repository

Use the official Espressif TinyCBOR component
Pin espressif cbor 0.6.1~4 unless a compatible version is already locked and proven

Target esp32p4

Use C for firmware
Use Python only for host scripts tests and small tooling
Do not introduce C plus plus

Never guess an API from memory
Before using an ESP IDF or component API inspect the installed header and the matching official example from the pinned version
Record the exact component and IDF versions in PROJECT_STATE.txt

BOARD FACTS

Inspect the repository

SECURITY ARCHITECTURE

The v0.1 credential design uses wrapped non discoverable credential IDs

During make credential

1 validate the CTAP request
2 calculate SHA 256 of the relying party ID
3 wait for a fresh button press
4 generate a fresh P 256 private key using the hardware random source
5 derive the P 256 public key with the hardware accelerated ECC path
6 place the private scalar and relying party hash in a fixed size plaintext record
7 wrap that record with AES 256 GCM using a fresh 96 bit nonce
8 put the wrapped record in the credential ID returned to the relying party
9 build authenticator data
10 sign packed self attestation with the new credential key
11 zero temporary private material

During get assertion

1 validate the CTAP request
2 hash the relying party ID
3 inspect credential IDs in allowList
4 authenticate and decrypt each candidate credential ID
5 accept only a valid record with the same relying party hash
6 wait for a fresh button press
7 sign authenticatorData followed by clientDataHash with the recovered P 256 key
8 return a normal ES256 assertion
9 zero temporary private material

No per website private key database lives on the device
The relying party stores the opaque wrapped credential ID and returns it in allowList

Use this exact v1 credential blob unless a written decision explains a necessary correction

external credential ID

offset  size  field
0       4     ASCII P4K1
4       1     format version 1
5       1     internal algorithm value 1 meaning ES256
6       2     reserved zero
8       12    AES GCM nonce
20      64    ciphertext
84      16    AES GCM tag

total 100 bytes

plaintext before encryption

offset  size  field
0       32    rpIdHash
32      32    P 256 private scalar in big endian

AES GCM additional authenticated data

the first eight credential ID header bytes
followed by the fixed sixteen byte P4Key AAGUID

Use a full 128 bit GCM tag
Never reuse a nonce under a wrapping key
Reject any wrong size magic version algorithm reserved bytes tag private scalar or relying party hash
Compare hashes and authentication values without early secret dependent exits
The credential ID parser takes an explicit pointer and length and performs every length check before reading

DEVELOPMENT ROOT AND HARDWARE ROOT

First make the device work with a development wrapping root

The development root is a fresh random 32 byte value stored in NVS
Create it once
Do not print it
Do not include it in crash logs
Mark this mode clearly as unsuitable against physical flash extraction

After website registration and login work add the optional hardware root mode

Use one ESP32 P4 eFuse HMAC key configured for upstream use
Access it through the supported ESP IDF PSA opaque HMAC interface
The eFuse key itself never becomes software readable
Derive the 32 byte AES wrapping key as HMAC SHA 256 over a fixed context string plus the AAGUID plus the credential format version

Never burn an eFuse automatically

No test
No script
No Codex session
No build target
No provisioning helper may execute an irreversible eFuse write

A helper may inspect eFuses
A helper may generate the exact command into a text file
The human must run that command separately
The helper must require an explicit board confirmation and still stop before executing the burn

The dedicated ESP32 P4 ECDSA signing peripheral is not the per website credential signer
That peripheral expects a small number of protected hardware keys
WebAuthn needs many independent credentials
Use the general P 256 ECC acceleration through ESP IDF Mbed TLS or PSA for credential key generation and ECDSA signing
Do not silently enable a dedicated eFuse ECDSA signing configuration for this path

CRYPTO PATHS

The required hardware use is

esp_fill_random or the supported ESP IDF entropy path for credential keys and GCM nonces
before treating it as true random confirm the P4 main entropy source remains enabled under the pinned startup configuration
if the main source is not continuously enabled use the supported entropy enable flow or a strong DRBG seeded while true entropy is available
never generate credentials from output documented as pseudo random only
hardware SHA 256 through the ESP IDF crypto stack
hardware AES and GCM through the ESP IDF crypto stack
general hardware ECC acceleration for P 256 multiplication and ECDSA
optional dedicated HMAC hardware for the root key

Compile time configuration must require the relevant hardware acceleration settings
A release build must fail or emit a loud explicit error when a required hardware path has been disabled
Do not claim hardware acceleration merely because Mbed TLS compiled
Add a script that checks sdkconfig and the build configuration
Add on target known answer tests
Add a simple benchmark comparing the configured path with documented build facts
Do not add a fake software fallback in the release profile

RSA and the RSA digital signature block have no natural job in this project
Do not invoke them only to say every accelerator got used

FIDO USB REQUIREMENTS

Use one USB HID interface for the FIDO authenticator

HID usage page 0xF1D0
application usage 0x01
input usage 0x20
output usage 0x21
64 byte input reports
64 byte output reports
no report ID
one interrupt IN endpoint
one interrupt OUT endpoint

Use the official TinyUSB stack rather than writing the device controller driver

Keep the TinyUSB callbacks short
Copy a complete 64 byte report into a fixed queue and return
Do not parse CBOR
Wait for a button
Run crypto
Touch NVS
or perform logging from a USB interrupt or callback context

Run CTAPHID and CTAP processing in a normal FreeRTOS task
Use fixed buffers
Avoid heap allocation in the transport path

Support at least four allocated channels in a fixed table

Handle channel busy
invalid channel
invalid command
invalid sequence
invalid length
message timeout
cancel
and a new broadcast INIT request

Use the broadcast channel 0xffffffff only for INIT

Return protocol version 2
Return capability flags for CBOR and no message command

Send keepalive while waiting for user presence
Use a 100 to 250 millisecond cadence
Do not exceed the protocol limit
Honor cancellation
Do not send a signature after cancellation

CBOR RULES

Use TinyCBOR or another already pinned official component
Do not write a general CBOR implementation

Create small strict helper functions around the library
Every helper takes input length
Every copy has a destination capacity
Reject indefinite length input for structures where fixed definite input keeps the parser simpler
Reject excessive map array string and byte lengths
Limit nesting
Reject trailing bytes after the top level object
Never use an unchecked integer conversion
Negative COSE keys and algorithm minus 7 must remain signed values

Encode maps in deterministic simple order
Canonical CBOR is not required by CTAP for every response but deterministic output makes tests easier
Do not build CBOR through string concatenation

USER PRESENCE

A button press proves user presence

A press that occurred before the current operation cannot approve it
Clear stale state at operation start
Debounce the GPIO
Require press then release
Use a finite timeout around 25 to 30 seconds
Send keepalive processing while waiting
A cancel or disconnect aborts the wait
No key generation or signature response after cancellation
The fake button backend used in tests must follow the same state machine

PERSISTENCE

v0.1 stores only

the development root when development mode is selected
small device configuration such as root mode and format version where needed

It does not store per site credentials

NVS initialization must handle a fresh device
Do not erase all NVS automatically after a generic error
Do not reset a root silently because doing so invalidates every registered credential
When the root cannot be loaded fail closed and display a clear serial error without printing secret data

COUNTER

The WebAuthn signature counter remains zero for all credentials in v0.1
This is allowed for an authenticator that does not implement a counter
Document the limitation
Do not fake incrementing state that cannot be kept safely for a stateless credential design
